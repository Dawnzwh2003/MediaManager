# Phase 4 metadata / thumbnail 验证（2026-11-08，Windows）

范围：用户本次授权的 metadata 和后台 thumbnail cache。未实施播放器、Event Service 或浏览 UI；未使用私人媒体，测试全部使用临时 SQLite 与合成文件。

环境：rustc/cargo 1.99.1、Node 24.22.2、npm 11.19.1；便携 FFmpeg/ffprobe 9.0.2-essentials_build-www.gyan.dev。工具来自 FFmpeg 官网下载页所列的 Gyan Windows 构建，位于忽略的 `.tools/ffmpeg/`，未更改系统 PATH。工具获取先在沙箱内失败，再经批准下载；未把下载失败计为功能测试通过。

有意义的新增覆盖：

- jpg/jpeg/png/webp/gif/bmp 六种图片；视频尺寸、时长、codec、fps；JPEG 由真实 FFmpeg 独立解码验证。
- 视频首帧红色、0.1 秒后蓝色，2 秒视频的输出采样为蓝色，证明使用约 10% duration 帧。
- 合成损坏图片/视频及未知 AVI FourCC；缺 ffprobe/FFmpeg、子进程非零退出、输出超限、超时、运行中取消；后续进程成功证明槽位释放。
- thumbnail 失败仍保留成功 metadata；缓存目录被普通文件占用的写失败及恢复；无临时文件冒充 ready。
- ready 多次请求/重开不再生成、缓存删除后重建、移动保留 ID/标签/Like/进度、同路径替换新 ID/零继承；原件字节不变。
- 内容版本失效与播放进度隔离、迟到结果拒绝、metadata/path/status 同事务 rollback、running 中断恢复、missing 暂停与 restored 恢复；两次 worker 启动去重及实例锁生命周期。
- 键包含 ID/版本/fingerprint/stat/生成配置，移动不改键、独立媒体不共享键、用户 ID 无法形成目录穿越；空/截断 JPEG 不标 ready。

本轮中间检查发现 Windows 扩展路径使图片自动探测进入 image2，现以单文件 demuxer 修复。首次未知 codec 测试只改 MP4 sample tag，FFmpeg 仍能从配置识别编码，因此改为真正未知的 AVI FourCC 合成样本。Clippy 检出新增测试模块位置及既有扫描的参数过多/无效 drop，已通过移动测试模块、汇总 ScanRun 参数及移除无效 drop 修复；不改变扫描业务规则。

限制：Windows 通过数不含 Unix 条件编译链接用例；本轮未运行原生 UI smoke、正式 release 打包或 100,000 UI 性能验收，前端页面未变。LRU/配额、工具发布/许可及 WebView 播放能力仍是后续范围。旧 Phase 1 浏览器专项状态保留。
